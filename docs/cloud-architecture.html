The shape of it

Two tiers that never block each other. The web containers serve screens and finish in milliseconds; the five job workers chew through tenders that take half an hour each.

The six components that do the work$269/mo

Everything a tender actually passes through, from the upload to the stored result.

Job worker container

ECS Fargate · ×5 · 1 core / 4 GB $213 / mo

The five always-running instances, and the reason this design exists. Each one takes a single tender off the queue and works through it: unpack the vendor folders, classify each document, send the text to be read, store the extracted facts. Five run in parallel, so five tenders can be in flight at once.

Why they cost the same idle as busy They are up around the clock whether work is arriving or not — that is what "always running" means. On a quiet day four of the five sit warm and empty, and the bill is identical. You are buying readiness: a tender that arrives at 4pm starts at 4pm instead of waiting for a machine to boot.

Web / API container

ECS Fargate · ×2 · ½ core / 1 GB $36 / mo

Everything people actually see. One process serves every screen and every /api route from a single address — the front end is compiled into the same image, so there is no separate web server to configure.

Why two, not one A single container makes every deployment an outage and every crash a total one. Two is the availability floor, not a capacity decision. It scales to four when a lot of people are on the system at once.

Job queue

SQS + dead-letter queue $0.20 / mo

The handover between the two tiers, and the single most important component on this page despite costing twenty cents. An upload becomes a message; a worker takes it when it has capacity. If a worker dies mid-tender the message reappears and another one picks it up.

What it is really solving A tender is roughly 102 model calls in sequence — about 34 minutes. A load balancer closes an idle connection after 60 seconds. Without the queue the browser's request dies less than two minutes in, and there is no way to finish the job at all.

System file store

EFS · 50 GB $15 / mo

The system of record: user accounts, the RFQ workflow, the bidder registry, and every stored tender result. Shared by all seven containers, which is precisely why it cannot be local disk — container storage disappears when the container does.

The expensive tier Thirteen times the price per gigabyte of the document store beside it. That is the argument for keeping only small, frequently-written files here and putting bulk documents in S3.

Document store

S3 · 500 MB today $0.01 / mo

Every uploaded drawing, datasheet and vendor proposal, stored under a fingerprint of its contents so the same file uploaded twice takes one copy. At 500 MB it costs about a penny a month; at 5 terabytes it would still cost less than the load balancer.

Worth knowing about the 500 MB That is roughly eleven tenders. At the measured rate of paperwork arriving, the store passes 500 MB in the first week and reaches about 26 GB after a year — which is still under a dollar a month. Storage is genuinely not where the money goes here.

Logs

CloudWatch Logs $5 / mo

What happened, and when. Answers "why did this tender fail last Tuesday" without anyone guessing. Ingestion is the cost, not storage — writing logs is what you pay for, keeping them is nearly free.

The eleven that support them$184/mo

None of it processes a tender. All of it is needed for the six above to be reachable, secure and recoverable.

Load balancer

Application Load Balancer $46 / mo

The single public front door. Terminates HTTPS once, then sends each visitor to a web container that is actually healthy — and stops sending traffic to one that is not, which is what makes a crash invisible rather than an outage.

Internet egress

NAT Gateway ×2 $68 / mo

Lets the workers reach the model provider's API while remaining unreachable from the internet themselves. Two, one per availability zone, so losing a zone does not stop every tender at once.

The line to question first The second-largest supporting cost, and charged by the hour whether traffic flows or not. Dropping to one is the cheapest saving available here and the only one that buys a worse system — not recommended.

Private AWS access

VPC endpoints ×8 $58 / mo

Direct private routes for pulling the container image, writing logs and reading secrets, instead of pushing that traffic out through the NAT gateway and back. Pays for itself, because image pulls and log shipping are most of what would otherwise be metered there.

Backup

AWS Backup $10 / mo

Scheduled snapshots of the file store. That store holds award decisions and there is no second copy anywhere, nor any way to re-derive it. The cheapest insurance on this page against the most expensive possible failure.

Secret storage

Secrets Manager ×3 $1 / mo

Keeps the model provider's API key out of the container image. The project's own build file spells out the alternative: anyone who can pull an image with a baked-in key can read that key, and image layers cannot be edited afterwards — only replaced, and the key rotated.

Image registry, network, scheduler, DNS, certificate, monitoring

ECR · VPC · ECS · Route 53 · ACM · CloudWatch $1 / mo

Grouped because together they cost about a dollar. One stored image that both the workers and the web containers run — the only difference between them is the start command. The private network the containers sit in with no public address. The scheduler that restarts anything that dies. The hostname, the auto-renewing certificate, and the alarms.

The alarm that matters Queue depth. A queue that stops draining means work is arriving faster than five workers can clear it — which is the one signal that the "five" in this design has become too few.

Five things that must be builtnot purchasable

Every component above can be bought. These cannot — the software is written today as a single machine doing everything, and three of these gaps stop the design working at all.

Move tender processing into the queue

C1blocks launch

Today a tender is processed inside the browser's own request, which cannot survive the 34 minutes it takes. It needs to become a queue message a worker picks up, with the browser checking back for progress.

Replace the in-process job lock

C2blocks launch

The guard that stops one tender being processed twice lives inside a single Python process, so it cannot see the other four workers. With five running, two can start the same tender and write over each other's results.

Implement the S3 document store

C3blocks launch

Documents are written to local disk today, which no other container can read. The storage interface was written expecting this, so it is a new implementation rather than a redesign.

Decide how the bidder registry is written

C4workaround available

The registry is a SQLite file, and SQLite on shared network storage with several writers can corrupt. The free fix is to route every registry write through one nominated worker; the durable fix is a managed database, which adds cost.

Add token metering

C5billing only

Nothing counts the tokens spent. The costs here can be budgeted, but not attributed to a particular department, project or tender. This one does not block launch — it blocks charging anyone for it.

Where the money goes

Two halves that behave completely differently — and understanding the difference is more useful than any single number here.

Cloud services are rented by the hour, like a hire car. An idle container costs exactly what a busy one costs. The five workers are $213 a month whether they process one tender or a hundred.

Reading documents is charged per document, like postage. A quiet month costs almost nothing on this half. It only rises when more paperwork genuinely arrives.

Because the five workers run around the clock either way, a busy month costs more almost entirely because more documents arrived — not because the servers worked harder. Peak assumes that rush is sustained for a whole month, which no month ever does; it is a ceiling, not a forecast.

The largest single saving available is running the five workers on spare capacity, which cuts that $213 by about 70% and costs nothing in design — an interrupted job already returns to the queue for another worker to pick up.

What is deliberately absent

Things a reader may expect to find, and the reason each one is not here.

A separate web server

nginx

The application already serves the API and the front end from one process and one address. A proxy would add a hop and a second configuration to keep in step.

A managed database

RDS

Every store is a file today. This appears only if the bidder registry (C4) is solved by moving to a database rather than by narrowing who writes to it.

A cache layer

Redis

There is no cache in the software, and nothing here is read-heavy enough to need one. It would be a component to operate in exchange for no measurable gain.

A content delivery network

CloudFront

The front-end bundle is small and comes from the same address as the API. Worth adding when users are spread across continents.

GPU capacity

accelerated instances

No model runs on our own hardware. Every model call is an outbound request to the provider, which is why the workers need memory rather than processing power.

Kubernetes

EKS

Roughly $75/month of control plane plus real operational burden, to schedule seven containers that the simpler scheduler already handles.

Separate infrastructure per team or project

—

One organisation, one shared store. Who can see what is controlled inside the application, not by running separate copies of it.

How firm are these numbers. The document-reading figures are derived from replaying a real tender through the production code, so the rates behind them are measured rather than guessed. Everything about the cloud is an estimate: prices are US list prices copied by hand and will go stale, and the workers are sized at one core and 4 GB each because a container's size is fixed when it starts — so it has to be sized for the largest tender, not the average one. Hosting in the UAE rather than Virginia adds roughly 15–20%. Every assumption is listed and editable on the Assumptions tab of the accompanying workbook.
