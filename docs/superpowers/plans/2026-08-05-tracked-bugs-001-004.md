## How this plan uses PLAN-TEMPLATE.md

[`PLAN-TEMPLATE.md`](../PLAN-TEMPLATE.md) is written for a phase that builds new
accumulating collections. This is a bugfix set, and applying its rules honestly
means saying where they bind and where they do not:

- **Rule 1 (store invariant per task).** Binds on tasks 1 and 5. Tasks 2, 3, 4
  and 6 do not write to the store at all — they are a factory guard, a test
  harness, front-end nav and front-end copy. Rather than invent an invariant for
  them, each declares `none — writes nothing to the store` and says what it
  guards instead. An invented invariant is worse than an absent one: it makes
  the checklist pass while defending nothing.
- **Rule 2 (two-run mutation matrix).** Binds on **task 5**, `force`. A forced
  full re-extraction is the widest-blast-radius write the system has and has
  never been exercised from the API; it is exactly a two-run behaviour and
  cannot be seen in one. The nine required rows are about the *cache-respecting*
  path, and this task's mutation is the cache bypass itself, so the matrix is
  built around what `force` changes and what it must not.
- **Rule 3 (reference code is intent).** Banner above, and each block below says
  which parts are load-bearing.

### Task 1: `POST /ingest` refuses an unconfigured deployment

**Files:**
- Modify: `api/main.py` (`_provider_state`, `ingest`)
- Modify: `procurement/pipeline.py` (`run_ingestion`, the `run.started` event)
- Test: `tests/test_api_setup.py`

**Interfaces:**
- Consumes: `os.environ["LLM_PROVIDER"]` (now optionally absent), request payload
- Produces: `_provider_state() -> {"provider": str | None, "ready": bool, ...}`;
  `ingest` returns 400 when no provider resolves
- **Store invariant owned:** a rejected ingest leaves the store byte-identical —
  `generation` does not move, `documents.json` and every `facts` collection are
  unchanged, and no `run.started` event is appended.

That invariant is the point of the task, not a side effect. The existing
comment at `api/main.py:382` records that an unvalidated server default once
"wrote a whole store of failed extractions while reporting `has_results: true`".
The guard added then checks the effective provider is known and configured —
and `mock` satisfies both, so the default slipped through the guard built to
catch it. The fix is to stop manufacturing an effective provider out of nothing.

Three call sites read the same default. All three change:

| line | today | after |
|---|---|---|
| `api/main.py:259` | `os.getenv("LLM_PROVIDER", "mock").lower()` | `os.getenv("LLM_PROVIDER")`, may be `None` |
| `api/main.py:394` | same, inside `ingest` | same; `None` → 400 |
| `shared/llm/factory.py:17` | same | task 2 |

`_provider_state` returning `provider: None` is a contract change the front end
sees. `needs_key` is `None` and `ready` is `False` in that state — `ready` must
not be computed by `_provider_ready(None)` returning something incidental.

**Load-bearing in the reference below:** that the 400 is raised *before* the
`try` and before `get_client`, and that its message names `LLM_PROVIDER`.
Illustrative: the exact wording.

```python
requested = (payload or {}).get("provider")
provider = str(requested).strip().lower() if requested else None
effective = provider or (os.getenv("LLM_PROVIDER") or "").strip().lower() or None
if effective is None:
    raise HTTPException(
        status_code=400,
        detail=(
            "No extraction provider is configured. Set LLM_PROVIDER in the API "
            f"environment (one of: {', '.join(PROVIDER_KEYS)}) and restart it, "
            "or name a provider in this request."
        ),
    )
```

The `run.started` event gains the client class, per §1.3 of the spec:

```python
detail={"client": type(client).__name__}
```

One key on an event already being written. It touches no snapshot, no cache key
and no generation bump.

### Task 4: BUG-001 — review screens gate on project status

**Files:**
- Create: `web/src/nav.ts`
- Modify: `web/src/App.tsx`, `web/src/pages/ComplianceMatrix.tsx`,
  `web/src/pages/ComparativeStatement.tsx`
- Test: `web/src/nav.test.ts`, `web/src/App.test.tsx`

**Interfaces:**
- Consumes: `ProjectSummary.status`
- Produces: `reviewReachable(status: string | null | undefined): boolean`
- **Store invariant owned:** none — front-end only, reads no store. It guards
  the rule that screens `02` and `03` are reachable only for a project whose
  store holds an extraction to read.

The decision from §1.1 of the spec: `done` and `done_with_failures` admit,
`new` and `failed` do not. An unknown status — a value from a newer API — is
treated as **not** reachable; the safe direction for an unrecognised state is
the one that shows the user the honest screen rather than an empty matrix.

`open()` at `App.tsx:40` is half the bug: it jumps to `matrix` unconditionally,
so opening a freshly created project from the dashboard lands on the compliance
matrix. It must send an unreachable project to `setup` instead.

The banner for `done_with_failures` says some documents failed and points at
`04 Extraction status`. It does not name them — see §1.1; naming them means
fetching `/extraction-status` from two screens that do not otherwise need it.

**Load-bearing:** the four status values and which side of the line each falls
on; unknown → false. Illustrative: the function name and the banner wording.

```ts
// web/src/nav.ts
const REVIEWABLE = new Set(['done', 'done_with_failures'])
export function reviewReachable(status: string | null | undefined): boolean {
  return status != null && REVIEWABLE.has(status)
}
```

### Task 5: BUG-002 — reach the existing `force` bypass

**Files:**
- Modify: `api/main.py` (`ingest`), `web/src/api.ts`, `web/src/types.ts`,
  `web/src/pages/Setup.tsx`
- Test: `tests/test_api_setup.py`, plus a two-run pipeline test module

**Interfaces:**
- Consumes: `{"provider"?: str, "force"?: bool}` on `POST /ingest`
- Produces: `run_ingestion(..., force=force)` reached from HTTP
- **Store invariant owned:** after a forced run, every stored collection
  contains exactly the records of its currently-live sources — the same
  invariant an ordinary run owns, held under the cache bypass. Concretely: a
  forced run re-extracts every live document, prunes the facts of every
  superseded/reclassified/deleted one, and bumps `generation` exactly once.

`run_ingestion` already takes `force: bool = False` and already does the right
thing. The entire defect is that nothing can set it, so the API change is one
field. The design work is the guarding, per §1.2: default `false`, a separate
secondary button shown only when `has_results`, and a confirmation naming the
cost. It must stay hard to hit by accident — a forced run re-spends the full
LLM cost of the project.

The tracker asks that whoever fixes this check what a forced run does to
`_prune_orphan_facts` and to the generation counter **before** exposing it.
That is Step 1b below, and it is a measurement, not an assumption: if a forced
run turns out to bump generation twice or to skip the prune, that is a second
bug to file and this task stops until it is understood.

- [ ] **Step 1: Write the failing API test** — `{"force": true}` re-extracts a
      document whose cache key is otherwise unchanged; `{}` and `{"force":
      false}` do not. Assert against the `document.extracted` /
      `document.skipped` events of the second run.
- [ ] **Step 1b: Measure the blast radius before exposing it** — drive
      `run_ingestion(..., force=True)` directly against an already-ingested
      fixture and record: how many times `generation` moves, whether
      `_prune_orphan_facts` runs, and whether any collection is left holding a
      record whose source is gone. Write down the measured numbers. **If
      generation moves more than once per run, or the prune does not run, stop
      and file it** — do not expose the switch over a broken write.
- [ ] **Step 2: Run to verify the tests fail**
- [ ] **Step 3: Implement** — API field, `runIngestion(slug, provider, force)`,
      and the guarded button
- [ ] **Step 4: Run the full suite plus `npm test`**
- [ ] **Step 4b: Two-run mutation matrix**

  Every row is two runs against one project, the second run forced unless the
  row says otherwise. Each defends the invariant named above.

  | mutation between run 1 and run 2 | invariant at risk | assert |
  |---|---|---|
  | nothing changes; run 2 forced | forced run re-extracts rather than serving cache | every live document appears as `document.extracted` in run 2, not `document.skipped` |
  | nothing changes; run 2 **not** forced | the bypass is opt-in and did not become the default | run 2 skips the unchanged documents, exactly as today |
  | a newer revision of an extracted document arrives; run 2 forced | facts of the superseded document are pruned, not merely skipped | no stored fact cites the superseded `doc_id` |
  | a document is deleted from its vendor folder; run 2 forced | no collection holds a record whose source is gone | no stored fact cites the deleted `doc_id`; no `DocumentRecord` for it survives |
  | a vendor folder is removed; run 2 forced | the stale-vendor sweep still runs under force | that vendor's facts collection is gone |
  | a document is reclassified between runs; run 2 forced | facts of the old route do not survive alongside the new | the document's facts come from exactly one extractor |
  | the LLM fails on a document during the forced run | a failed re-extraction never blanks previously-good stored data | the prior good facts survive, and `DocumentRecord.notes` records why |
  | run 2 forced, then run 3 forced | generation bumps once per write transaction, never once per file | generation moves by exactly 1 per forced run |

  Verify the matrix is real: reinstate each defect one at a time and confirm the
  intended row fails — and that nothing else does. A row that still passes with
  its defect reinstated is not testing what it claims.
- [ ] **Step 5: Commit**
