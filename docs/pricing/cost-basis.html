How this was measured

Every input below comes from the repository or a real ingested tender. Nothing is a market comparable.

  • Workload — replayed projects/phase4c-shipped-defaults through the production code paths (loaders.read_text, VENDOR_ROUTE, chunk_on_lines at the shipped 12,000 and 8,000-character budgets). That yields the true call count and the exact character volume a real run sends.
  • Prices — current Anthropic first-party rates per million tokens.
  • Tokenisation — calibrated with count_tokens against synthetic text that reproduces the corpus's layout geometry exactly: same line lengths, same indentation, same 62% whitespace share. No client document text was sent anywhere.
The one number that is inferred

Output volume is taken from what the run actually stored — 217,819 characters of compact fact JSON — plus a 15% allowance for empty and failed calls and tool-call envelope. ask_each_chunk uses items.extend with no de-duplication, so stored output is a close proxy for what the model emitted rather than a compressed summary of it.

Where the 102 calls come from

The order matters here: each stage decides how much work the next one sees, and two of them are already doing real cost control.

  1. 01 Classification — filename rules run first, and the model is consulted only when they decline, on 500 characters of head text. 34 of 37 documents matched a rule and cost nothing. 3 calls
  2. 02 Routing — VENDOR_ROUTE sends specs, BOMs, drawings, minutes and datasheets all to the technical extractor. Quotations additionally take a secondary datasheet pass. —
  3. 03 Technical extraction — chunked at 12,000 characters. This is the bulk of the bill: one 220,933-character proposal alone is 19 chunks. 88 calls
  4. 04 Quotation, requirements and deviation — whole-document for quotations, chunked at 8,000 for the client requirement sheet. 11 calls

The credit unit

A credit has to be model-agnostic, or every model swap silently re-prices the product. Define it against one reference model and express the others as multipliers.

1 credit = 1,000 tokens of Sonnet-5-equivalent work

The measured workload is 74% input / 26% output, which blends to $6.09 per million tokens on Sonnet 5. That makes one credit cost $0.006086 to serve, and one tender ingest 473 credits.

Multipliers are blended at this workload's 74/26 mix. If a future feature is output-heavy the multipliers shift, so recompute them per workload rather than treating these four as constants.

Why this argues for the credit model

A seat costs us between one and three dollars a month in infrastructure and nothing else. All the real cost is the tenders that seat actually runs, and that varies by a factor of eight across the rows above. A flat per-seat price either overcharges the light user or loses money on the heavy one — which is exactly the case for charging the seat cheaply and the work by the credit.

What would move these numbers

Four things, roughly in order of how much they matter. The first is a blocker, not an optimisation.

Blocker — nothing records token usage

There is no usage accounting anywhere in shared/llm/ or procurement/. No call records input_tokens or output_tokens, and events.jsonl logs actions but not consumption. You cannot bill credits you do not measure, and the estimate on this page cannot be validated against reality until the client layer returns usage and the pipeline stores it per run. That is the first thing to build.

  • 62% of what we send is whitespace. pdftotext preserves column layout, so nearly two thirds of the 1.2M input characters are padding. Collapsing runs would cut input volume by about half — but input is only 37% of the bill, so the ceiling here is roughly a 20% saving, and column alignment is exactly what lets the model keep a value with its unit. Measure recall before touching it.
  • The Batch API halves everything. Ingestion already runs as a background job, so asynchronous turnaround costs almost nothing in user experience. This is the single largest lever on the page.
  • Re-ingestion is already free. Extraction caches on content hash plus prompt version, so re-running a project only pays for documents that actually changed. A prompt-version bump re-prices every document in every stored project — budget for that when shipping one.
  • Two features would add real cost. The LLM vision fallback for scanned PDFs is wired but production passes pdf_fallback=None, so those five unreadable drawings cost nothing today; turning it on prices images, not text. LlamaParse is in the tree but unreachable — production passes pdf_reader=None — and is per-page billed if it ever ships. The RFQ extractor is still a fixture; at ~10 credits a call it stays negligible.
