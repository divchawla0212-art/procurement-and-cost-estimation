Process specification · Rev. 1

How the platform runs an RFQ

Eight stages from scoping a package to issuing a purchase order, four of them guarded by a gate that refuses in writing. This is the document behind that behaviour: what each stage does, what it records, what will stop it, and the rules that hold across all of them.

Orientation

What this system is, in one paragraph

A request for quotation is a document trail before it is a transaction. Someone scopes a technical package, decides which vendors may see it, sends it out, answers their questions in writing, opens what comes back, evaluates it, negotiates, and issues a PO. Every one of those steps produces a record that a later audit will read, and the expensive failures are almost never arithmetic — they are a vendor invited without a valid prequalification, an answer that went to one bidder and not the rest, a package amended after issue with no numbered addendum to prove it.

So the platform models the process, not just the paperwork. An RFQ occupies exactly one stage at a time. Movement between stages is a deny-by-default transition table, and four of the forward edges run an exit gate first. A gate that refuses says why, in a full sentence, and the API returns that sentence as a 409. Nothing advances quietly.

Reading the diagram

Four marks, four meanings

Stage node

One of the eight process steps. An RFQ is in exactly one at any moment, and its whole history of arrivals is kept.

Gate

An exit criterion evaluated on the forward edge. Solid means it can refuse; a dashed outline marks an edge that is open by design.

Refusal

The literal sentence the system returns. Reproduced verbatim throughout — this copy is part of the contract, not illustration.

Recovery edge

A sanctioned move backwards: retender, renegotiate. Never gated — a forward gate must not trap a stuck RFQ.

The process, end to end

Eight stages, top to bottom

1
RFQ-01Stage.SCOPING

Scoping

An RFQ is raised against a project and the specific items it covers, then a technical package is assembled against it — a basis of design plus the attachments vendors will bid from, each with its document code and revision. The stage ends when that package is frozen: an explicit, attributed act that fixes the revision every bidder will be quoting against.

CreatesRfqRecord — reference, project, item ids, package, discipline, value estimate. TechnicalPackage — revision, basis of design, attachments.
EndpointsPOST /rfqs, PUT /rfqs/{id}/technical-package, POST /rfqs/{id}/technical-package/freeze
CaveatsAn item whose required_on_site falls outside the project's live period is stored anyway, with a warning returned beside it. A hard refusal would make the field unusable in exactly the case worth recording — a late delivery. Freezing is one-way: after it, set_technical_package refuses, and the only route to a change is an addendum at RFQ-04.
Gate — Scoping → Shortlisting

A package exists, and it is frozen.

  1. A technical package has been attached to this RFQ. 
    No technical package has been attached to this RFQ; one must be attached and frozen before shortlisting can begin.
  2. That package has been frozen. 
    The technical package must be frozen before shortlisting can begin.

Note that the first message names both halves of the criterion. A user told only "no package" attaches one, retries, and is refused again for something nobody mentioned. Every refusal in this system states the whole exit criterion rather than the nearer half of it.

2
RFQ-02Stage.SHORTLISTING

Shortlisting

Candidates come from an organisation-wide bidder registry, and the platform scores each one against this RFQ at read time: a list of blockers — somebody's explicit refusal — and a list of cautions, facts worth seeing that decide nothing. Inviting a blocked bidder is permitted but requires a written reason, so it becomes a positive attributed act rather than a silent edit. The stage also fixes the technical bid evaluation criteria and the vendor document register (VDRL) that bids will be checked against later.

BlockersOn hold; prequalification suspended, under review, or declined; prequalification lapsed (derived from prequal_expires_on against the date you ask on).
CautionsExpiry within 30 days; not on the client's Approved Vendor List; not registered for this discipline.
CreatesShortlistEntry (per invited vendor), TbeTemplate, VdrlLine, plus a procurement approval of the set.
EndpointsGET /rfqs/{id}/candidates, POST /rfqs/{id}/shortlist, POST /rfqs/{id}/shortlist/approve, PUT /rfqs/{id}/tbe-template, POST /rfqs/{id}/vdrl
CaveatsA registry-linked entry's vendor name, prequal status and scope fit are derived from the registry and any contradicting values in the request are ignored — otherwise a caller could link a suspended bidder and label the entry qualified. Adding or removing any vendor revokes the shortlist approval, because an approval is of a specific set. Scope matching is whole-string and case-folded, never substring: "Electric" must not answer for "Electrical Testing", a different trade whose bid would be thrown out at evaluation.
Gate — Shortlisting → Issued

Someone to send it to, signed off, with criteria to judge by.

  1. At least one vendor is included. 
    The shortlist contains no included vendors.
  2. Procurement has approved the shortlist as it currently stands. 
    The shortlist must be approved by procurement before issuance.
  3. A TBE template is attached. 
    A TBE template must be attached before the RFQ can be issued.
3
RFQ-03Stage.ISSUED

Issued

The frozen package goes out to the included shortlist, with the VDRL and the original bid due date. This is the moment the record stops being internal: from here, what the vendors hold is a fact about the outside world, and every subsequent change to it has to be numbered, dated and circulated.

FixesThe package revision bidders quote against; the original due date; who was invited.
CaveatsThere is no gate on the edge into Clarifications — the round opens as soon as the RFQ is out, because a bidder can ask a question the same afternoon.
Open edge — Issued → Clarifications

Permitted by the transition table, with no exit criterion to evaluate. The stage advances on request.

4
RFQ-04Stage.CLARIFICATIONS

Clarifications

Two registers run in parallel. Queries are questions from named invited bidders, numbered TQ-001 or CQ-001 by category, answered with attribution and a timestamp. By default an answer is circulated to the whole included shortlist; withholding it requires a written restriction reason, so unequal treatment is always a recorded decision rather than an oversight. Addenda are numbered amendments to the issued package — the one sanctioned door through the freeze — drafted, edited freely, then issued, at which point they supersede the package at a new revision and become immutable.

Query statesOpen, Answered, Withdrawn — computed from three timestamps, never stored. Withdrawal is checked before an answer, so a query answered and then withdrawn is out of the round.
NumberingHighest + 1, never count + 1. A withdrawn query keeps its number, so a count-based sequence would hand a second bidder a number already quoted to a first.
EndpointsPOST /rfqs/{id}/queries, .../answer, .../withdraw, POST /rfqs/{id}/addenda, PATCH, .../issue, DELETE
CaveatsAn issued addendum can be neither edited nor deleted — bidders hold it. Issuing runs four checks: the package is frozen; the addendum still supersedes the package's current revision; it moves the revision; and every attachment carries a definite revision. The operative bid due date is derived from the latest issued addendum that names one — a date nobody has been told about is not a date.
Gate — Clarifications → Bids Received

Nothing outstanding before the envelopes are opened.

  1. No query is still open — every one is answered or withdrawn.
  2. No addendum is still in draft — every one is issued or deleted.
Bids cannot be opened while there are queries still open (TQ-002, CQ-001) and addenda still in draft (ADD-02). Answer or withdraw each query, and issue or delete each draft addendum.

Both failures are recoverable in principle and unrecoverable in practice. Once the bids are open, a bidder who never got their answer cannot be given one, and a package change that was drafted and never issued cannot be issued. The message lists whichever halves are actually true, with the specific numbers.

5
RFQ-04AStage.BIDS_RECEIVED

Bids Received

Bids are registered with their arrival time, headline price and currency, and each one is checked off against the VDRL: every mandatory document is marked received, not_received or unreadable. A named person then selects which bids go forward, with a rationale. Selection narrows what is evaluated; the bids not selected stay in the register.

Returnablesunreadable is deliberately distinct from not_received — a corrupt file is a delivery failure to chase, not a refusal to submit. Only received counts toward the completeness figure, so the count never flatters a bid.
CreatesBid, VdrlReceipt, BidShortlist — the last carrying who selected, why, and when.
CaveatsOptional VDRL lines are not counted as gaps. A selection with an empty rationale, an empty bid list, or a bid belonging to another RFQ is refused outright.
Gate — Bids Received → Evaluation

Somebody has decided what is being evaluated.

Bids must be selected for evaluation before evaluation can begin.
6
RFQ-05Stage.EVALUATION

Evaluation

The selected bids are compared technically against the TBE criteria fixed at RFQ-02, and commercially against the item estimates. This is where the wider platform's document pipeline does its work — vendor submissions are classified, revision lineage resolved, and parameters extracted per document class.

Hard ruleArithmetic stays in code. Extraction captures numbers and units verbatim; no model is ever asked whether a vendor complies. The model reads, code decides.
ExitsForward to Negotiation, or backward to Issued — a retender.
Open edge — Evaluation → Negotiation

No exit criterion. A recommendation is a judgement, and the system does not pretend to hold the evidence that would let it check one.

↑↑ Retender — Evaluation may return to Issued when no bid is acceptable. Ungated, and it appends to the history rather than rewriting the first pass.
7
RFQ-06Stage.NEGOTIATION → Stage.AWARDED

Negotiation, then Award

One process step, two states. Terms are agreed at Negotiation and the approval chain completes at Awarded — which is why the enum has nine members for eight stages. Splitting them means an RFQ sitting in approval is distinguishable from one still being negotiated, without a second status field to keep in step.

ExitsNegotiation → Awarded, or Negotiation → Evaluation, a renegotiation. Awarded → PO Issued.
Open edge — Negotiation → Awarded → PO Issued

Neither edge carries an exit criterion in this revision. Named per-stage approvals are a deferred requirement — see the limits section below.

↑ Renegotiate — Negotiation may return to Evaluation. Like retender, it is a documented recovery and no forward gate may block it.
8
RFQ-07Stage.PO_ISSUED

PO Issued

Terminal. The transition table gives this stage an entry with an empty set of successors rather than omitting it, so asking "may this RFQ move to X?" answers no instead of raising. That is a small thing that matters at an API boundary: an unknown edge and an impossible one should not fail differently.

Cross-cutting

Eight rules that hold at every stage

These are not stage behaviour; they are properties of the whole subsystem. Most of them exist because their absence has cost somebody something, here or elsewhere in this codebase.

01

The check lives inside the lock

Every write, and every decision that authorises one, happens inside a single locked read-modify-write. A check made in the route and a write made in the store are two critical sections: two concurrent transitions would each read "gate open" and both proceed. Every guard this codebase has shipped wrong was a read outside the lock, never a write.

02

Transitions are deny-by-default

An edge absent from the table is refused. Every stage has an entry, including the terminal one. Backward edges exist only where they are documented recoveries, and forward gates never apply to them.

03

A refusal is never a bare false

Gates return a result carrying a reason, the store raises with it, and the route surfaces it as a 409 with the sentence intact. The reason names the whole exit criterion — the failure mode being designed against is a user who fixes the half they were told about and is refused again.

04

Derived, never stored

Prequalification expiry, query state, the client-approval gap and the operative bid due date are all computed at read time from fields that already say them. A stored copy is wrong the moment its source is edited, and keeping it honest would need a sweep job nobody has written.

05

Nothing is deleted under a live reference

An item covered by an RFQ, a project holding one, a bidder on a shortlist, a shortlist entry that raised a query — each refuses deletion and names what is holding it. Persistence replaces the document wholesale, so a dangling reference does not merely misbehave in memory; it survives the restart.

06

Missing data is never coerced

An unknown value is absent, not zero, not an empty string, and never a passing default. A shortlist entry with no vendor named and an assumed "qualified" status is precisely the record these rules exist to prevent.

07

A snapshot is not a mirror

A shortlist entry records what the registry said at the moment somebody decided to invite that vendor. A later rename or suspension does not rewrite it. What was known at the time of the decision is the fact an audit needs — it is a different fact from what is true today, and both are kept.

08

History is append-only

A backward transition appends an entry; it never rewrites or removes an earlier one. A second pass through a stage is a second entry, which is why the target stage alone is not a unique key within one RFQ's history.

Shape of the data

What holds what

Indentation is containment. Everything binds by id — names are user-editable text and list positions are not a contract, so no reference anywhere is made by name or by index.

Project1
Name, code, client, location, a live period, currency, status. The top-level container; deleting one cascades to its items in the same write, and is refused outright while any RFQ exists under it.
Item0..n per project
Type, description, quantity, unit, discipline, estimated value, required-on-site date, long-lead flag. An update never touches id or project_id: moving an item between projects would change which project's RFQs may cover it without either RFQ record changing.
RfqRecord0..n per project
Reference, the item ids it covers, package name, discipline, value estimate, current stage, and the full append-only stage history.
TechnicalPackage0..1 per RFQ
Revision, basis of design, attachments, and — once frozen — when and by whom. Replaced wholesale each time an addendum is issued.
ShortlistEntry0..n per RFQ
The invitation. Optionally links a registry Bidder; carries the snapshot of name, prequal status and scope fit, plus an override reason where one was required.
TbeTemplate · VdrlLine1 · 0..n per RFQ
What bids will be judged on, and what documents they must return. Both fixed before issue.
ClarificationQuery · Addendum0..n per RFQ
The clarification register and the package's revision trail. A query addresses the shortlist entry that raised it, not the registry bidder — only someone invited to this RFQ can ask about it.
Bid · VdrlReceipt · BidShortlist0..n · 0..n · 0..1
What came back, what was in it, and what goes forward.
Bidderorganisation-wide
Held once for the whole organisation rather than retyped per RFQ, because prequalification is a company-level fact with a validity period. Deliberately outside the project tree.
Integration notes

What you should know before you call it

  • Persistence is one document, replaced wholesale The workflow lives in a single JSON document behind one lock and one atomic write, in the same pattern as the accounts store. The store itself knows nothing about disk — serialization is isolated in one module, so replacing the file with a database is a change to that module alone. The consequence for you: any field added to the store needs a matching line in both directions of that module, or it silently fails to survive a restart.
  • Every workflow path requires a session No workflow route is on the public allowlist, which stays pinned at three paths and is enforced by a test that sweeps every registered route. Roles are admin and reviewer, set once at creation; no route changes a role. Restarting the API signs everyone out by design — the server-side session rows are cleared at startup, so a still-held cookie is inert.
  • Errors map predictably 404 for an unknown id, 409 for a refused transition or a guarded deletion — carrying the sentence verbatim, which is intended for display — and 422 for a malformed body. If you are building UI against this, render the 409 text rather than substituting your own; it is written to be read by the person who has to act on it.
  • Nothing imported from a real vendor list is embellished Where the registry is seeded from a client's Approved Vendor List export, every field the sheet does not carry is left empty — no expiry, no hold, no turnover, no rating, and no country, since the only country in such an export is the manufacturer's. These are real, named companies, and a synthesised suspension is indistinguishable on screen from a recorded one.
  • The client-approval gap is a caution, never a blocker A vendor absent from the client's AVL is flagged wherever they appear, but eligibility is unchanged and no path it opens demands an override. The sentence is built in exactly one place, so the roster, the registry card and the RFQ view cannot drift apart in what they say.
Deliberate limits

What this revision does not do

Stated plainly, because a gap you know about is a scoping decision and a gap you discover is a defect.

  • No bid window timers The due date is recorded and derived correctly, but nothing closes a window automatically or refuses a late bid. Registration is a human act with a recorded arrival time.
  • No named approval gates per stage Four of the eight forward edges are gated. The Evaluation → Negotiation → Awarded → PO Issued edges are open, so award authority is a process convention today, not something the system enforces.
  • No item-type catalogue Item types are free text against a shared vocabulary by convention. A catalogue was deferred until persistence existed; it now can be built.
  • Returnables checking is VDRL-only Presence and readability of the mandatory document set is checked. Content-level compliance of those documents is the evaluation pipeline's job, and is not part of the gate.
  • No document storage or SSO in this layer Attachments are recorded by document code, title and revision — the register, not the file. Object storage and federated identity are open infrastructure questions rather than pending code, and the answer changes the shape of the work more than any other input.
